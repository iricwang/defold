# 人员工作页与版本审阅（第 0–2 批）

本轮保持项目总览布局、常驻 AI 工程清单和引擎默认主题，复用项目 `work.json`、原有人员执行队列与人工审批。没有增加外部文档服务或另一套执行状态。

## 使用入口

- 总览的职员行、Person 卡右键“打开职员工作页”：同一 `staff-id` 复用同一页签，展示跨 Canvas 队列、负载、负责的 Task、成果版本和待确认返修。
- 总览“查看任务”进入 Task 页签，展示负责人、范围、交付要求、验收检查、依赖、执行记录及固定输入版本，可进入原 Canvas 和对话。返回总览保留筛选，关闭其他页签保留总览和常驻清单。
- Result / Assets 详情中的“版本与审阅”，或总览“成果版本待批准”、职员页成果条目，打开固定版本审阅窗口。
- 不同 Result 的横向对比继续使用 Action 右键“对比方案”；审阅窗口“对比历史版本”只列同一 `bundle-id` 的版本。

## 第 0 批：编辑保护

1. 固定成果只读。直接保存归档 Markdown 会被拒绝；普通创作 Markdown 仍使用原编辑入口。
2. “基于此版本修改”创建或恢复该父版本的工作副本。正文和 Markdown 可在窗口编辑；图片可替换为同格式文件，其余类型用外部应用编辑副本后“重新收集”。
3. 保存检查台账修订和磁盘内容；冲突保留输入，不覆盖外部修改。未保存时禁止切换资源，退出窗口前要求保存或撤销未保存内容。
4. 提交时核验父版本、工作文件和实际冻结副本，在同一台账事务中登记成果及草稿提交状态。文件收集失败不会登记半个成果。草稿不会继承批准或验收。
5. 新版本记录 `parent-id`、`draft-id`，沿用原方案 `bundle-id`。旧文件、批准、已固定任务输入及正式工程不被自动更新。采用审阅版本时，确认队列绑定所选 artifact，避免再次复制为另一个版本。

文件保护是应用入口和摘要校验；不是操作系统写保护。用户在外部程序直接改动归档后，原有摘要准入会阻止继续使用该版本，应从备份恢复。

## 第 1 批：人员与 Task

- 使用原有项目队列；只调整 `queued`、`blocked`、`paused` 项的相对顺序。
- 执行器按台账顺序选取本 Canvas 可执行任务，并继续通过项目级 `claim!` 保证同一人员只有一个执行槽位。
- `running` / `unknown` 不可移动，也不允许被当作空闲重新执行。阻塞项不占用独立工作的执行槽位。
- 页面左右分区分别滚动；刷新保持滚动位置，替换子控件前保护焦点，避免全局菜单上下文落到已移除控件上。页签关闭后停止自身刷新计时器。

## 第 2 批：审阅与返修

- 意见绑定固定 artifact ID 和修订。Markdown 行范围必须在正文/文件实际行数内；图片使用归一化区域。历史意见可定位到文件、选中行段或显示图片区域。
- 检查清单逐行填写，`[x]` 表示已通过、`[ ]` 表示待核对，随该次版本意见保存。
- 提出返修时选择负责人并填写具体问题；先保存 `review` 提案，不创建执行工作。没有 Task 的历史成果可记意见，需先通过 AI-PM 补充分配。
- 总览“待我处理”和对应职员页显示返修。点击“确认分配并加入负责人队列”后，复用 AI-PM 分配创建独立返修 Task / Canvas，保留原任务与验收；后续执行仍从 Person 队列推进。
- 返修保留原 Canvas 类型、交付要求、必要验收检查和固定版本引用，重复确认复用同一任务。人工确认方案继续独立排队，不阻止无依赖的后续 Action；每个 Result 可分别选择。

## 数据兼容与恢复

`work.json` 增加 `review-drafts`、`review-notes`、`rework`，没有改变既有字段含义。旧项目缺少这些集合时视为空，不重建审批或重新分配旧任务。工作副本位于 `ai-workspace/candidates/drafts`，不加入用户侧常驻文件清单；冻结文件继续使用既有 artifacts 归档。

恢复基线为本轮开始时 `dev` 的 `13bb1233b1a9b2f1ea96b594c68dd09628cf300a`。工作区原有 `patch/channel.json` 修改保持原样；真实游戏已验收数据未参与测试写入。项目恢复需一起保留 `work.json`、Canvas、冻结文件和正式工程，不能仅复制聊天或单个 Canvas。

本轮不包含第 3–5 批的资源发布类型扩展、AI-PM 增量重规划、跨项目模板迁移及文件回收站。
