# PhotoCraft IP binding

Use File → Bind PhotoCraft by IP to connect to a PhotoCraft instance (default 17655). PhotoCraft connects to the editor on 17654 through its Defold Sync panel. PhotoCraft periodically tries loopback, including after this editor restarts; Defold independently discovers the local opener. `-Ddefold.craft.port=<port>` changes this editor listener. The binding channel uses HTTP on a trusted local network and does not expose `.internal/editor.token`.

The connection belongs to the current project directory, independent of the selected GUI tab. Connecting or reconnecting never saves or closes documents. Open tabs, dirty resources and PhotoCraft undo history stay intact. Local connections are accepted without a save/close prompt; remote connections ask only to connect the project. Pending file operations or a build can delay connection. Cancellation while a commit is queued still wins. Each PhotoCraft instance has an independent authenticated session: adding a connection keeps existing connections alive, and renewing or releasing one ticket affects only that peer. File → PhotoCraft Binding Status shows the address or last error.

Local loopback sessions share the original project directory without copying files. Remote sessions transfer ordinary project resources with bounded traversal and SHA-256 digests; reconnecting reuses the existing mirror and editable sources. Hidden files/directories, build/target output, symbolic links and editable `.pcraft` sources are excluded. Limits: 20,000 files, 64 MiB per file, 1 GiB per project, 128 levels. PhotoCraft caches native editable sources separately and refreshes project resources explicitly. Generated uploads are restricted to `photocraft_generated/`. Named resources support atomic replacement guarded by an expected SHA-256 checksum; deletion requires that no static project resource still references the path. Legacy immutable uploads remain available, and authored game resources are never overwritten by this endpoint. The legacy eval route uses the existing editor-extension runtime and now accepts loopback callers only. It does not implicitly open the linked GUI; opening a tab is a separate explicit action. Legacy synchronization does not save the GUI; the structured publication below uses an exact target save and durable receipt.

File → Open GUI in PhotoCraft sends the active GUI to the selected bound application. With multiple connections it prompts for the target. File → Disconnect PhotoCraft removes only the selected connection; Binding Status lists all addresses and this editor's actual listening port. If the resource was created after initial binding, refresh the project resources in PhotoCraft first.

A GUI tab's context menu includes **Open in PhotoCraft**. It is enabled only while a running PhotoCraft responds on the local binding port (17655); discovery runs every five seconds, including when Defold is bound to a remote peer. Other resource tabs do not show this action. The action uses the context resource, confirms any required project connection change while retaining all documents, and reopens the GUI in Defold after sending it to PhotoCraft. Cancelling the binding does not open the file.

Regression coverage lives in `test/editor/craft_binding_test.clj`: consent/idle barriers, cancellation races, session authorization, path validation, immutable uploads and manifest exclusions/content digests. A standalone local HTTP harness also exercises the actual Clojure routes against the production Rust transport in both directions. The headless adapter does not validate JavaFX dialogs or the complete editor runtime. Patch packaging and install/restart verification must be performed with the exact installed baseline using `patch/README.md` before publication.

When a restarted local PhotoCraft takes over the same listening socket with a new instance ID, discovery releases only that stale identity. It does not release a remote client, another listening port, a client already bound elsewhere, or a session with in-flight operations. The new instance then reconnects through the ordinary project handshake without saving or closing files.

## Structured project adapter, version 1

The project host discovers this adapter through `.internal/photocraft/editor-adapter.json`, containing `schemaVersion`, the actual `port`, and a UUID `editorSessionId`. No credential is copied to discovery. The host must send `.internal/editor.token` as a Bearer token over loopback. The legacy peer identity remains separate for compatibility; `/binding/eval` rejects LAN callers even if they possess a binding ticket.

The project-root `.photocraft` directory is reserved, like `.internal`: collaborative sources, leases and publication journals never enter the editor resource graph or trigger a game-resource refresh. Other unknown files are still inspected; saving collaboration metadata does not weaken conflict detection for game assets.

All adapter routes are POST JSON, with a 4 MiB control limit:

- `/craft/v1/project`: capability and session description; independent of open GUI tabs.
- `/craft/v1/snapshot` with `{path}`: background-load the resource and return `source`, `dirty`, `diskHash`, `sceneHash`, `editorGraphRevision`, and `editorSessionId`. It does not select/open a tab, save, or clear Undo.
- `/craft/v1/resource/open` with `{path}`: an explicit reveal action opens or focuses one native resource tab and returns `{schemaVersion:1,path,opened:true}`. The path must be a registered, editor-openable file in this project, with no hidden segments, traversal or symlinks. Custom/external editors and OS-open plans are forbidden. Snapshot and publication never invoke this action automatically.
- `/craft/v1/publish/prepare`: validate and durably record a plan before changing game files.
- `/craft/v1/publish/apply` with `{transactionId, planHash}`: enqueue one publication and immediately return its status.
- `/craft/v1/publish/status` with `{transactionId}`: retrieve durable progress or the same completion receipt.
- `/craft/v1/publish/cancel`: only a PREPARED publication can become ABORTED; later stages require reconciliation.

Prepare accepts `{schemaVersion:1, transactionId, planHash, editorSessionId, targets, resourceUpdates}`. Each target has `{path, expectedDiskHash, expectedEditorGraphRevision, changes}`. Changes contain the full desired `nodes:[{id,parent,kind,values}]`, `textures:[{name,texture}]`, and `renames:[{from,to}]`. Native node kinds use names such as `gui-node-type-box`. Rotations are finite three-component Euler angles; the native GUI setter stores valid quaternions. Reparenting requires explicit final parent-local position, rotation and scale. Box/text/pie replacement retains surviving descendants; template override reparenting and custom node replacement are rejected explicitly.

Prepare rejects undeclared native properties and checks writable properties on existing nodes without editing the graph. Apply commits size-mode controls before resolving dependent setters such as slice9. A property with a native getter and the same semantic value needs no write, including unchanged read-only defaults. Unknown properties and real changes to read-only properties remain errors with node/property context; values are never discarded silently.

Each resource update contains `{action:"create"|"replace", path, expectedDiskHash, newContentHash}`. Hashes use `sha256:<64 lowercase hex>`. The adapter reads fixed content-addressed staging files at `.internal/photocraft/transactions/<transactionId>/files/sha256-<digest>`; caller-supplied staging paths are never accepted. PNGs are bounded and decoded before installation. Atlas descriptors are parsed by Defold. The host writes staging only; this adapter is the sole executor of game-file installation. Move is represented by a new path with the previous path retained. Delete and physical garbage collection are separate operations.

New assets and stateless image invalidation use a preflighted, explicitly scoped resource refresh. Any unrelated disk change or resource-node replacement fails with `UNDO_BARRIER_REQUIRED` before changing the workspace snapshot. Existing atlas content is edited on its original graph resource node, never replaced through disk reload. All GUI and atlas graph edits run in one editor callback and one Undo operation. A graph failure restores that operation. Native Undo does not delete installed PNGs or restore their previous pixel bytes.

The adapter freezes only the affected GUI/atlas save data and invalidation counters, then saves those exact versions in background I/O. Ordinary save/reload, legacy writes, restart and close are guarded while publication is active. Later editor edits remain dirty. States are PREPARED → APPLYING → APPLIED_UNSAVED → SAVING → COMMITTED; failures after apply require RECOVERY_REQUIRED. Multi-file disk I/O is not an atomic filesystem transaction. Original exact bytes are retained under their baseline content hashes, and frozen sources remain in `.internal/photocraft/adapter-transactions/<transactionId>.json` for reconciliation. Restart never silently replays a nonterminal publication.

If apply cannot claim the editor's file-operation gate, it returns `TARGET_BUSY` while its durable state remains PREPARED and no game files have changed. The host can inspect that explicit state and retry the same transaction/plan; an unknown transaction after an uncertain apply still requires reconciliation. Gate ownership compares transaction ID values across independently decoded requests, so completion releases the gate before subsequent publications can proceed.

A COMMITTED receipt includes `targets:[{path,diskHash,sceneHash,editorGraphRevision,editorAhead}]` and `resources:[{path,diskHash}]`. Atlas hashes are the actual Defold-serialized disk bytes, which can differ from staged TextProto bytes. Scene/revision fingerprints identify the frozen saved source, even if the editor has newer dirty changes. The host must verify these files and complete its own registry/journal commit before reporting project publication success. Retrying a transaction returns its prior receipt; reusing an ID with altered content is rejected.

`sceneHash` hashes the native GUI protobuf value with schema defaults expanded, so omitting explicit defaults on reload does not change scene identity. Node/resource order and every known protobuf field remain significant; unknown fields are rejected by the native parser. This hash is tied to the editor's protobuf schema, not a cross-version migration guarantee. `editorGraphRevision` separately hashes the exact frozen native save text and remains a session-scoped compare-and-swap token. After an editor session changes, obtain a fresh snapshot and revision; `diskHash` still identifies exact persisted file bytes. Older durable receipts retain their original fingerprints.

Regression namespaces: `editor.craft-publish-test`, `editor.craft-binding-test`, `integration.craft-project-test`, `integration.craft-publish-test`. They cover temporary native graph projects, multi-target rollback, staged PNG/atlas publication, targeted saves, newer dirty edits, reparent/type changes, continuous Undo/Redo across asset registration, idempotency, discovery, and loopback isolation. They do not substitute for exact-baseline incremental patch installation and restart verification.

## Multiple project connections (binding protocol 2)

Defold and PhotoCraft both support many-to-many sessions. One project may connect several PhotoCraft instances; one PhotoCraft may keep several Defold projects connected. Add bindings by IP/port without closing or saving other documents. Choose the current project connection in PhotoCraft's Defold Sync panel; document synchronization resolves the document's own project rather than the selected panel connection. Incoming GUI-open requests retain the originating session and project, including when another project is selected. When more than one editor for the same project is connected, select the intended editor before synchronizing.

Status exposes `bindingVersion: 2` and `boundPeers` (IDs only), while retaining the legacy `bound` field. Old clients can continue using a single connection; full many-to-many behavior requires updating both applications. A handshake is serialized, but adding a peer does not suspend existing authenticated resource requests. Tickets are unique per pair, renewed credentials invalidate only that pair, and delayed releases cannot revoke another peer.

Multiple instances use the default listener where available, otherwise an automatically allocated port. Explicit `defold.craft.port` and `PHOTOCRAFT_BIND_PORT` overrides still fail if occupied. Use each application's binding status/panel to see its actual port; project-local `.internal/photocraft/editor-adapter.json` records the editor port without credentials.
